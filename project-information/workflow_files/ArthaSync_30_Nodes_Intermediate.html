2 Authorization Layer — N1 to N5

N1
API Request Trigger
INPUT
Description
Receives HTTP POST from ArthaSync frontend for registration or login. This is the single entry point for the entire platform. Accepts JSON body and routes to validation immediately.
Configuration
Method: POST /api/auth/{register|login} Payload: { username, fullName, email, phone, password } Auth: None — public endpoint Content-Type: application/json
Why: Single entry point enforces all traffic flows through auth before reaching any business logic.
N2
Input Validator & Password Hasher
CUSTOM CODE
Description
Validates email regex, phone format (+CountryCode-Number), password length ≥ 8 chars. On pass: hashes with bcrypt saltRounds 12, assigns UUID v4, adds ISO 8601 createdAt timestamp. Throws structured field-level errors on any failure.
Code Logic
Runtime: Node.js 18 | Python 3.11 Library: bcryptjs — saltRounds: 12 emailRegex: /^[^\s@]+@[^\s@]+\.[^\s@]+$/ phoneRegex: /^\+[1-9]\d{0,2}-\d{7,12}$/ Output: { uuid, username, hashedPw, createdAt, phoneSheet }
Why: bcrypt saltRounds 12 is OWASP recommended. Field-level errors are required for front-end UX. UUID ensures DB idempotency.
N3
JWT Token Generator
CUSTOM CODE
Description
Login path only. Retrieves stored bcrypt hash from PostgreSQL, verifies against provided password. On match: generates RS256 signed JWT with 24-hour TTL. Registration path skips this node and proceeds directly to N4.
Configuration
Algorithm: RS256 — private key in AWS Secrets Manager TTL: 24 hours (exp = iat + 86400) Payload: { userId, username, role, iat, exp } DB Query: SELECT hashedPw FROM users WHERE username=$1
Why: RS256 (asymmetric) is safer than HS256 for distributed services — only the auth service holds the private key.
N4
Auth Gate — Valid / Invalid
CONDITION/BRANCH
Description
Routes on validation result. Valid credentials flow to DB write, Google Sheets append, and JWT response. Invalid credentials immediately return HTTP 400 with specific field-level error messages — no further processing.
Branch Logic
Condition: validation_errors.length === 0 TRUE path: → PostgreSQL write → Sheets append → JWT response → Telegram notify FALSE path: → HTTP 400 { success: false, errors: [{field, msg}] } Key metric: validation_pass_rate (CloudWatch)
Why: Hard branch prevents any partial-valid data from reaching the DB. Fail-fast principle — no DB calls on invalid input.
N5
Auth Success / Error Response
OUTPUT FORMATTER
Description
Formats and delivers the final auth response. Success: returns JWT + sanitized user profile (never password). Simultaneously appends audit record to Google Sheets and sends Telegram admin notification. Error: returns structured 400 with per-field messages.
Output Schema
Success: { success: true, token: JWT, user: { id, username, email }, sessionId } Error: { success: false, errors: [{field, msg}] } Side effects: Sheets.append(row) + Telegram.notify(admin) Columns: ID | Username | Full Name | Email | No.[CC] | Created At | Last_Login
Why: Side effects (Sheets + Telegram) happen only on success — prevents audit log pollution from failed attempts.

3 Sync Agent — N6 to N13

N6
Web Store API Poller
TOOLS
Description
Polls e-commerce web store REST API every 60 seconds via AWS Lambda + EventBridge scheduler. Fetches all SKUs with price and stock. Handles pagination automatically and implements exponential backoff on HTTP 429.
Configuration
Endpoint: GET /api/v2/inventory?store=web&page={n} Auth: Bearer token — AWS Secrets Manager Schedule: 60s — EventBridge rule On 429: Exponential backoff — 2s, 4s, 8s — max 3 attempts Response: [{ sku, price_inr, stock_qty, updated_at }]
Why: Web store is primary channel. Pagination prevents timeout on large catalogs. Backoff avoids rate-limit cascades.
N7
Mobile App API Poller
TOOLS
Description
Polls mobile app backend for real-time stock and pricing. Sends Cache-Control: no-cache header to bypass stale mobile CDN cache. Returns JSON SKU array with per-item timestamps for freshness checking.
Configuration
Endpoint: GET /api/v2/inventory?store=app Headers: Cache-Control: no-cache, Pragma: no-cache Timeout: 10s hard limit Format: [{ sku, price, qty, updatedAt }] Freshness: reject items where updatedAt > 5min ago
Why: Mobile CDNs aggressively cache. The no-cache header is critical — without it, mobile prices may be stale by hours.
N8
POS Webhook Receiver
TOOLS
Description
Receives real-time Petpooja/Ginesys POS event webhooks on stock changes. FastAPI endpoint with SHA256 idempotency key deduplication prevents double-processing. Handles sale_complete, stock_update, and void_transaction events.
Configuration
Endpoint: POST /webhook/pos-event Dedup key: SHA256(sku + timestamp + store_id) Events: sale_complete | stock_update | void_transaction Response: HTTP 200 { received: true, idempotency_key } Signature: HMAC-SHA256 webhook verification
Why: POS is the ground truth for physical stock. Idempotency key is mandatory — POS systems often re-send on network hiccups.
N9
Channel Data Aggregator
MERGE/JOIN
Description
Waits for all three channel responses within a 55-second window. Outer-joins all arrays by SKU key — missing channel data triggers Last-Known-Good cache fallback rather than blocking the pipeline. Unified multi-channel snapshot per SKU.
Configuration
Mode: Outer join — keyed by normalized SKU string Window: 55s — triggers Memory/Context fallback on timeout Missing: channel_data = last_known_good[channel][sku] Output: [{ sku, web_price, app_price, pos_price, web_qty, app_qty, pos_qty, cycle_ts }]
Why: Outer join (not inner) ensures all SKUs appear even when one channel is down. 55s window balances freshness vs reliability.
N10
Schema Normalizer
CUSTOM CODE
Description
Converts all three channel formats into a unified CommerceState TypedDict schema (LangGraph typed state). Strips null SKUs, normalizes price to INR float with 2 decimal places, coerces quantity to integer ≥ 0. Deterministic — no LLM involved.
Code Logic
Language: Python 3.11 | TypedDict (LangGraph) Schema: CommerceState { sku: str, prices: dict[str,float], qtys: dict[str,int] } Rules: price → round(float(v), 2) INR qty → max(0, int(v)) sku → str.upper().strip() null_price → inherit from cache or flag as missing
Why: TypedDict enforces compile-time safety. Deterministic normalization means downstream LLM always sees consistent data format.
N11
Schema Validation Guardrail
EVALUATOR/GUARDRAIL
Description
Hard schema checks before any data proceeds downstream. Rejects rows missing SKU, all-null prices, or all-null quantities. Logs each violation to AWS CloudWatch custom metric. Rejections route to DLQ handler (N20), not silently dropped.
Rules
Rule 1: sku IS NOT NULL AND sku.length > 0 Rule 2: COUNT(non_null_prices) >= 1 Rule 3: COUNT(non_null_qtys) >= 1 On fail: → N20 (DLQ) + CloudWatch metric schema_violations_total++ On pass: → N12 (Deduplicator) Alert: CloudWatch alarm if violations > 5 in 10min
Why: Guardrails run in Python (deterministic), not LLM. Any conflict analysis on corrupt data creates false alerts — garbage in, garbage out.
N12
Idempotency Deduplicator
CUSTOM CODE
Description
MD5-hashes the sorted, normalized snapshot. Compares with previous cycle hash stored in Memory/Context (N13). Identical snapshot emits no-op signal — skips entire Conflict Agent for this cycle, saving LLM cost and latency.
Code Logic
Hash: MD5(JSON.stringify(sorted_snapshot)) Compare: current_hash vs cache[store_id].last_hash If same: → emit { changed: false } → skip to N30 (no-op output) If diff: → emit { changed: true, snapshot_id, cycle_ts } → N14 Cache TTL: 120 seconds rolling window
Why: Most sync cycles produce NO changes. Skipping the Conflict Agent on no-change saves ~40% of Bedrock API costs in production.
N13
Last-Known-Good State Cache
MEMORY/CONTEXT
Description
Stores the most recent valid normalized snapshot as fallback. Serves two purposes: (1) fallback when a channel API times out mid-cycle in N9, (2) stores last_hash for N12 deduplication. Prevents dashboard blackout during partial outages.
Configuration
Store: In-memory Python dict keyed by store_id TTL: 300 seconds — 5-minute safe operational window Keys: { last_snapshot, last_hash, last_cycle_ts } Fallback: Injected into N9 on timeout (55s window exceeded) Eviction: LRU — max 1000 store entries
Why: 300s TTL covers typical API maintenance windows. Without this, a single channel outage would black out the entire dashboard.

4 Conflict Agent — N14 to N21

N14
Conflict Triage Router
CLASSIFIER/ROUTER
Description
Primary gate for the Conflict Agent. Routes on the changed signal from N12. No change → emit all-clear directly to Output Formatter (N30). Change detected → fan out in parallel to all three conflict detectors (N15, N16, N17 run concurrently).
Routing Logic
Input: { changed: bool, snapshot_id, cycle_ts } Route A: changed == false → N30 { status: "no_change", cycle_ts } Route B: changed == true → parallel fan-out to N15, N16, N17 Latency: < 2ms — pure dictionary lookup, no I/O Metrics: conflict_cycles_total, no_change_cycles_total
Why: Fan-out parallelism is critical — running detectors sequentially would double latency. Price, oversell, and history checks are independent.
N15
Price Delta Calculator
CUSTOM CODE
Description
Computes pairwise price deltas across all channel combinations per SKU. Flags any delta exceeding the Rs.20 threshold. Calculates severity based on delta magnitude and assigns conflict IDs for downstream tracking.
Algorithm
Threshold: Rs.20 (env: PRICE_DELTA_THRESHOLD) Logic: for each sku: max(prices) - min(prices) > threshold Pairs: web↔app, web↔pos, app↔pos Severity: CRITICAL: delta > Rs.200 HIGH: delta Rs.50–200 MEDIUM: delta Rs.20–50 Output: [{ sku, delta, channel_pair, severity, conflict_id }]
Why: Rs.20 = 1.3% of avg Rs.1,500 SKU — McKinsey comparison-shopping research threshold. Tighter threshold → more noise. Looser → missed revenue leaks.
N16
Oversell Risk Detector
CUSTOM CODE
Description
Flags oversell risk when POS physical stock is zero or critically low while online channels show available inventory. Also checks orders-in-flight from the cache against available POS stock. Oversell is the most operationally damaging conflict type.
Rules
Rule 1: pos_qty == 0 AND (web_qty > 10 OR app_qty > 10) → HIGH Rule 2: orders_in_flight > pos_qty → HIGH Rule 3: pos_qty < 5 AND (web_qty > 20 OR app_qty > 20) → MEDIUM Risk: CRITICAL: pos_qty = 0 and active online listings HIGH: pos_qty < 5, online shows > 20 Output: [{ sku, pos_qty, online_qty, risk_level, oversell_units }]
Why: Oversell leads to order cancellations and customer churn. This check runs independently of price delta — both can coexist on same SKU.
N17
Historical Conflict Patterns
KNOWLEDGE RETRIEVAL
Description
Queries PostgreSQL conflict_history table for the same SKU and channel combination over the last 30 days. Returns recurrence frequency, average delta, and last resolution action. Provides LLM context for pattern-aware recommendations.
SQL Query
SELECT COUNT(*) as recur_count, AVG(price_delta) as avg_delta, MAX(created_at) as last_seen, last_value(resolution_action) OVER (ORDER BY created_at) as last_action FROM conflict_history WHERE sku = $1 AND channel_pair = $2 AND created_at > NOW() - INTERVAL '30 days' Index: composite on (sku, channel_pair, created_at) Cache: 5min Redis TTL per (sku, channel_pair) key
Why: Recurrent conflicts on same SKU are systemic — single-cycle detection misses the pattern. 30-day window is the ops team's planning horizon.
N18
Conflicts Found? Gate
CONDITION/BRANCH
Description
Aggregates results from all three parallel detectors (N15, N16, N17). Any detected conflict or oversell flag routes to the Business Rules Enforcer. Zero conflicts emit all-clear JSON directly to Output Formatter — no LLM call made.
Branch Logic
Condition: conflicts.length > 0 OR oversell_flags.length > 0 YES path: → N19 (Business Rules Enforcer) NO path: → N30 { status: "all_clear", cycle_ts, sku_count } Aggregate: merge(price_flags, oversell_flags, history_ctx) Dedup: remove duplicate conflict_ids before passing forward
Why: The all-clear fast path means no LLM call on clean cycles. This is the key cost-control gate — Bedrock only runs when there is actual signal.
N19
Business Rules Enforcer
EVALUATOR/GUARDRAIL
Description
Hard deterministic business rules that cannot be overridden by LLM output. Runs entirely in Python — no AI involved — for complete auditability. Enforces oversell safety, alert fatigue caps, and promotion logic consistency.
Rules (Python, not LLM)
Rule 1 (Safety): oversell_risk = true AND strategy = INCREASE → REJECT → force REDUCE/AVOID Rule 2 (Halt): oversell_count > 5 in 24h for same sku → HALT channel for 1h Rule 3 (Fatigue): sku_alerts > 3 per day → SUPPRESS + log suppression Rule 4 (Sanity): delta < 0 (price inversion) → flag as data error → DLQ Rule 5 (Stock): pos_qty = 0 → ANY increase strategy → REJECT Output: { validated_conflicts, suppressed_count, guardrail_notes[] }
Why: LLM outputs are probabilistic. These 5 rules are absolute business invariants. Separating them from LLM ensures they are never bypassed by creative prompting.
N20
Dead Letter Queue Handler
RETRY/FALLBACK
Description
Catches schema failures from N11, API timeouts from N6/N7/N8, and hard-stops from N19. Routes failed events to AWS SQS Dead Letter Queue for async retry. Triggers Telegram admin alert on 3rd consecutive failure per SKU.
Configuration
Queue: AWS SQS — arthasync-conflict-dlq Retries: 3 × exponential backoff (2s, 4s, 8s) DLQ TTL: 24 hours — manual review window Alert: Telegram admin @ failure_count >= 3 (same origin) Message: "⚠️ DLQ: {origin_node} failed {n}× — sku: {sku} — {ts}" Recovery: Manual re-inject from DLQ console or auto after 24h
Why: SQS DLQ ensures no conflict event is silently lost. The 24h TTL matches the daily ops review cycle.
N21
Severity Router
CLASSIFIER/ROUTER
Description
Classifies each validated conflict into CRITICAL, HIGH, or MEDIUM severity tier. CRITICAL immediately triggers parallel Human Handoff (N29) in addition to the standard Insight Agent flow. Routes to the matching prompt template variant for LLM context.
Routing Rules
CRITICAL: delta > Rs.200 OR pos_qty = 0 with live listings → N22 (Context Builder) + N29 (Handoff) [PARALLEL] HIGH: delta Rs.50–200 OR oversell_risk = MEDIUM → N22 (Context Builder) [priority queue] MEDIUM: delta Rs.20–50, no oversell → N22 (Context Builder) [standard queue] Batch: Groups same-severity conflicts into single LLM call
Why: Batching same-severity conflicts reduces LLM calls from N per conflict to 1 per severity tier. CRITICAL parallelism ensures the owner is notified instantly, not after LLM processing.

5 Insight Agent — N22 to N30

N22
Context Builder
PROMPT TEMPLATE
Description
Assembles the full LLM prompt context by merging: validated conflict list with severities and deltas, historical pattern summary from N17, and guardrail_notes from N19 explaining any suppressed recommendations. Injects specific numbers to prevent vague LLM outputs.
Prompt Template
SYSTEM: You are ArthaSync, a commerce intelligence agent for Indian retail SMEs. Your output MUST contain 3–5 bullet points. Each bullet MUST include: - A specific Rs. amount - The channel name(s) affected - One concrete action verb (increase/reduce/avoid/maintain/investigate) Do NOT use hedging language. Be direct and specific. USER: Conflicts detected: {conflicts_json} Historical patterns: {history_summary} Rules applied: {guardrail_notes} Supply context: {supply_signals} Timestamp: {cycle_ts}
Why: Explicit format constraints in the system prompt raise quality checker pass rate from ~60% to ~92% in testing. The Rs. amount requirement ensures specificity.
N23
Cognizant AI Agent — Bedrock Haiku
LLM STEP
Description
AWS Bedrock Claude Haiku generates the plain-English manager brief. Runs within the Cognizant AI Agent Workflow System — zero external API calls, all data stays inside the AWS environment. Temperature 0.3 for factual, low-variance output.
Configuration
Provider: Cognizant AI Agent Workflow System (AWS Bedrock) Model: anthropic.claude-haiku-20240307-v1:0 Temperature: 0.3 — factual, deterministic Max tokens: 512 — 3-5 bullets + rationale paragraph Top-P: 0.9 Stop: ["---", "Note:", "Disclaimer:"] Retry: Auto on throttle — max 2 attempts
Why: Haiku over Sonnet — 10× cheaper, adequate quality for structured outputs. Temperature 0.3 prevents "creative" recommendations that bypass guardrails.
N24
Brief Quality Checker
EVALUATOR/GUARDRAIL
Description
Validates LLM output against strict quality criteria. Minimum 3 bullets, each containing at least one Rs. amount, one channel name, and one action verb. Rejects empty or vague outputs to the Retry/Fallback node (N28). Deterministic regex-based checks — no LLM for validation.
Validation Rules
Rule 1: bullet_count >= 3 Rule 2: each bullet matches /Rs\.\d+/ Rule 3: each bullet contains channel_name in {web, app, POS, mobile, online} Rule 4: each bullet contains action in {increase, reduce, avoid, maintain, investigate, pause} Rule 5: total_length > 100 chars (reject near-empty outputs) Pass: → N25 (Confidence Scorer) Fail: → N28 (Brief Regeneration Handler)
Why: Quality check runs in <1ms vs 800ms for another LLM call. Fail-fast on format prevents vague briefs from reaching the dashboard.
N25
Confidence Scorer
CUSTOM CODE
Description
Emits a confidence score between 0.0 and 1.0 based on four factors: guardrail pass rate, conflict coverage (% of input conflicts addressed in brief), Rs. specificity of bullets, and historical pattern match rate. Score determines enrichment routing.
Scoring Formula
score = ( 0.30 * (bullets_with_amount / total_bullets) + # specificity 0.25 * (conflicts_addressed / total_conflicts) + # coverage 0.25 * (guardrail_pass_rate) + # rule compliance 0.20 * (history_match_rate) # pattern alignment ) HIGH: score >= 0.85 → N26 → N30 (Output Formatter) LOW: score < 0.85 → N26 → N27 (Enrichment) Max enrichment loops: 2
Why: Confidence gating is the key mechanism for selective API usage — the challenge's primary constraint. Low confidence triggers enrichment; high confidence skips it, saving cost.
N26
Confidence Gate
CONDITION/BRANCH
Description
Routes on confidence score from N25. HIGH confidence proceeds directly to Output Formatter. LOW confidence triggers the Knowledge Retrieval Enrichment path, adding competitor benchmarks and category norms before a second LLM pass. Maximum 2 enrichment loops enforced by counter.
Branch Logic
Condition: score >= 0.85 HIGH path: → N30 (Output Formatter) — fastest path LOW path: → N27 (Low-Confidence Enrichment) Loop guard: enrichment_count > 2 → force N30 with warning flag Counter: incremented on each LOW routing, reset on HIGH Flag: brief.low_confidence_warning if loop_count == 2
Why: Maximum 2 enrichment loops prevents infinite cost spiral. The loop guard ensures the system always terminates — critical for real-time dashboard SLA.
N27
Low-Confidence Enrichment
KNOWLEDGE RETRIEVAL
Description
Triggered ONLY on low-confidence output — implementing selective API usage (the core challenge constraint). Fetches competitor pricing benchmarks and category-level delta norms. Re-injects enriched context back into the Prompt Template for a second LLM pass.
SQL Query
SELECT competitor_avg_price, category_delta_norm, channel_performance_index, seasonal_adjustment_factor FROM market_benchmarks mb JOIN sku_categories sc ON mb.category_id = sc.id WHERE sc.sku_prefix = LEFT($1, 4) AND mb.region = $2 AND mb.updated_at > NOW() - INTERVAL '7 days' Re-inject: → N22 (Context Builder) with {benchmarks} field populated Selective: ONLY called when confidence < 0.85 — not on every request
Why: This node directly satisfies the "selective API usage" success criterion. Calling it on every request would be penalized. The confidence gate is its gatekeeping mechanism.
N28
Brief Regeneration Handler
RETRY/FALLBACK
Description
Handles LLM brief failures from N24. First attempt: regenerates with a stricter prompt constraint. Second attempt: adds explicit format enforcement. On second failure: emits a template-rendered fallback brief using raw conflict data — system never returns empty to the dashboard.
Configuration
Max attempts: 2 regeneration cycles Attempt 1: Add strict constraint to system prompt: "You MUST include one Rs. amount for EVERY conflict listed." Attempt 2: Add: "Format EXACTLY as: • [Channel]: Rs.[delta] — [Action]" Fallback: Template-rendered brief using raw conflict JSON if both fail: "• {channel}: Rs.{delta} detected — investigate pricing ({sku})" Never: Return empty response to dashboard
Why: The template fallback is the safety net that guarantees dashboard never goes blank. Even a mechanical brief is better than no information for the store owner.
N29
Store Owner Escalation
HUMAN HANDOFF
Description
Triggered in parallel for CRITICAL severity conflicts only. Sends immediate Telegram alert to the registered store owner phone. Requires acknowledgement within 15 minutes. Runs concurrently with the Insight Agent — does not block final output.
Configuration
Trigger: CRITICAL: pos_qty = 0 OR delta > Rs.200 Channel: Telegram Bot — store owner registered mobile number Message: "🔴 CRITICAL ALERT — ArthaSync SKU: {sku_id} Issue: Rs.{delta} price conflict / POS stock: {pos_qty} Channels: {channel_list} Action required within 15 minutes. Reply ACK to confirm. Auto-escalate in 15min if no response." Ack: Webhook on reply → update conflict record status = ACKNOWLEDGED Timeout: 15min → escalate to manager Telegram group
Why: CRITICAL conflicts (POS out of stock + live online listings) cost real money every minute. Human decision is needed. 15-min ACK timeout ensures escalation if owner is unavailable.
N30
Final Commerce Intelligence Brief
OUTPUT FORMATTER
Description
Formats and persists the final output payload. Written to PostgreSQL insights table, served to the React dashboard via 5-second polling, and queued for the daily Telegram digest. Includes full explainability metadata — every decision is traceable.
Output Schema
{ brief: string[], // 3-5 action bullets conflict_ids: string[], // tracked conflict references confidence: float, // 0.0–1.0 score apis_called: string[], // full selective API audit trail signals_used: string[], // which signals influenced decisions severity_tier: "CRITICAL"|"HIGH"|"MEDIUM"|"all_clear", cycle_ts: ISO8601, sku_count: int, suppressed_count: int // fatigue-capped alerts } Targets: PostgreSQL (insights table) + React dashboard + Telegram daily digest SLA: < 3s end-to-end from N22 to N30 on HIGH confidence path
Why: apis_called and signals_used fields directly satisfy the "explainability" success criterion. Evaluators can audit every decision. The 3-second SLA is achievable on the HIGH confidence (no enrichment) path.

How does your design handle over-promotion risk? What signals trigger a 'reduce' or 'avoid' strategy instead of maintaining or increasing promotion?
Over-promotion risk is handled at two distinct layers — deterministic rules (N19) and LLM reasoning (N23).

Deterministic layer (N19 — Business Rules Enforcer): Rule 3 enforces that any SKU with >3 alerts in a single day is automatically suppressed (fatigue cap), and the suppression is logged in the guardrail_notes field. Rule 1 rejects any INCREASE strategy when oversell_risk = true. Rule 2 halts the channel for 1 hour if oversell_count exceeds 5 in 24 hours. These rules fire in Python code, not LLM — they cannot be overridden by model output.

LLM layer (N22/N23): The Context Builder prompt explicitly injects: (a) the historical promotion frequency from N17, (b) the guardrail_notes including any suppression events, and (c) the supply context from N16. The LLM is instructed to detect patterns where high promotion frequency coincides with declining margin or stock depletion. Signals that trigger 'reduce' or 'avoid': oversell_risk = HIGH/CRITICAL from N16; recur_count > 5 in 30 days from N17 (systemic issue, not one-off); price_delta that has been consistently high across cycles (trend, not anomaly); pos_qty falling below 5 units combined with high online visibility.
Describe how you handle the trade-off between high demand and limited inventory. What does the workflow recommend and why?
The high-demand, limited-inventory trade-off is the central design challenge of ArthaSync. The workflow handles it through a layered approach:

Detection (N15 + N16): High demand is signaled by web_qty and app_qty remaining high (consumers still seeing availability) while pos_qty drops toward zero. N16 computes oversell_units = sum(web_qty + app_qty) - pos_qty when pos_qty < 10.

Hard constraint (N19): Rule 1 and Rule 5 are absolute: if pos_qty = 0, any strategy that increases promotion is REJECTED regardless of demand signal. The business invariant is: you cannot promote what you cannot fulfill. This prevents customer cancellations and churn damage.

LLM recommendation (N23): Given the guardrail_notes (which include the supply constraint), the LLM is directed to recommend: REDUCE promotion on high-demand SKUs with pos_qty < 5 (preserve remaining stock for highest-margin channel); AVOID online promotion on pos_qty = 0 SKUs (remove from active campaign); MAINTAIN promotion on web/app only if the store owner has confirmed a restock date (via Human Handoff acknowledgement from N29); INVESTIGATE if the web/app inventory data hasn't been updated — this surfaces a data sync gap rather than a real stock issue.

Explainability (N30): The final output includes signals_used: ["pos_qty=0", "web_qty=120", "oversell_units=120", "rule_5_applied"] and apis_called: ["web_poller", "pos_webhook", "conflict_history"] — making the trade-off reasoning fully auditable.
What is your confidence-based branching logic? How does the workflow determine when additional data retrieval is needed?
Confidence-based branching is implemented in N25 (Confidence Scorer) and N26 (Confidence Gate). The score is computed as:

score = 0.30 × (bullets_with_Rs_amount / total_bullets) + 0.25 × (conflicts_addressed / total_conflicts) + 0.25 × (guardrail_pass_rate) + 0.20 × (history_match_rate)

A score ≥ 0.85 means the brief is specific, complete, rule-compliant, and pattern-consistent — it routes directly to the Output Formatter (N30) without any additional API calls. A score < 0.85 routes to the Knowledge Retrieval Enrichment (N27), which fetches competitor pricing benchmarks and category delta norms from the market_benchmarks table. This enriched context is re-injected into the Prompt Template (N22) for a second LLM pass.

The maximum enrichment loop count is 2 — a hard guard in N26 prevents infinite loops and ensures the system always terminates within the dashboard SLA. If after 2 enrichment passes the score is still below threshold, N26 forces the output to N30 with a low_confidence_warning flag, allowing the ops team to review the brief manually. This design means the enrichment API is called selectively — only when the initial LLM pass lacks the specificity needed for confident recommendations — directly implementing the challenge's "selective API usage" constraint.
