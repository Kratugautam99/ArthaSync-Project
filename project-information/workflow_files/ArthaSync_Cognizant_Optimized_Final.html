3 · Snapshot Hash Checkv2Custom Code
Creates a fingerprint of the snapshot and compares it to the last tick's fingerprint in Redis. If identical, we skip the entire pipeline.
Input (from node 2)
{ "shopify":[...], "amazon":[...], "pos":[...] }
Paste-ready Python (Custom Code node body)
import hashlib, json, redis, os

r = redis.from_url(os.environ["REDIS_URL"])

# 1. Build a stable string from the snapshot (sort_keys makes the order deterministic)
payload = json.dumps(input, sort_keys=True).encode()

# 2. MD5 fingerprint of the snapshot
current = hashlib.md5(payload).hexdigest()

# 3. Pull the previous tick's fingerprint for this tenant
key = f"snap:{context['tenant_id']}"
previous = r.get(key)

# 4. Store the new fingerprint with 3-minute TTL (survives brief outages)
r.setex(key, 180, current)

# 5. Tell the next node whether anything has changed
return {
    "changed": current != (previous or b"").decode(),
    "hash": current
}
Line-by-line explanation
  • import ... — pulls in MD5 (hashlib), JSON serializer, Redis client, and env-var reader.
  • r = redis.from_url(...) — opens a Redis connection. Redis is used because it's in-memory and sub-millisecond — the hash check must be faster than the API calls it prevents.
  • json.dumps(input, sort_keys=True) — turns the snapshot into a string. sort_keys=True is critical: without it, the same snapshot could produce different hashes just because dict-key order changed.
  • hashlib.md5(...).hexdigest() — produces a 32-char fingerprint. MD5 is fine here (not cryptographic use; just change-detection).
  • key = f"snap:{tenant_id}" — namespaces the key per tenant so two tenants never collide.
  • r.setex(key, 180, current) — stores the new fingerprint with a 3-minute expiry. If the next tick is delayed, we still have a fresh baseline.
  • return {"changed": ..., "hash": ...} — the downstream Condition node reads $.changed to decide whether to continue.
Output
{ "changed": true, "hash": "a4f1c2...", "snapshot": {...original payload passed through...} }

Stage 1 · Sync Agent (Normalize)

4 nodes · harmonizes three channel schemas into one canonical record
6 · Normalize SchemaCustom Code
Flattens vendor-specific field names (e.g. Shopify's variant_sku, Amazon's SellerSKU) into one canonical shape. Keeps the LLM focused on ambiguous cases, not field-name translation.
Input
{ "shopify":[{"variant_sku":"RICE-5KG","inventory_quantity":42,"price":480}, ...], "amazon":[{"SellerSKU":"RICE_5KG","Quantity":38,"ListingPrice":495}, ...], "pos":[...] }
Paste-ready Python
MAPPING = {
    "shopify": {"variant_sku":"sku", "inventory_quantity":"qty", "price":"price"},
    "amazon":  {"SellerSKU":"sku",   "Quantity":"qty",           "ListingPrice":"price"},
    "pos":     {"item_code":"sku",   "stock":"qty",              "mrp":"price"},
}

def normalize_one(row, source):
    out = {}
    for k, v in row.items():
        # if we know how to rename the field, use the canonical name; else keep original
        out[MAPPING[source].get(k, k)] = v
    out["_source"] = source
    return out

normalized = []
for src in ("shopify", "amazon", "pos"):
    for row in input[src]:
        normalized.append(normalize_one(row, src))

return {"rows": normalized}
Line-by-line
  • MAPPING = {...} — dictionary of dictionaries. Outer key is the channel name; inner dict maps channel-specific field to canonical field. Cheap to maintain when a new channel is added.
  • MAPPING[source].get(k, k) — the .get(k, k) pattern returns the mapped name if it exists, otherwise keeps the original. Safe fallback.
  • out["_source"] = source — stamps the row with its origin so downstream can still tell where it came from.
  • Triple-nested loop — O(n) over all rows. No LLM call here — this is pure deterministic work, which keeps cost near zero.
Output
{ "rows":[{"sku":"RICE-5KG","qty":42,"price":480,"_source":"shopify"}, {"sku":"RICE_5KG","qty":38,"price":495,"_source":"amazon"}, ...] }

Stage 2 · Conflict Agent

10 · Rule-Based Conflict DetectionCustom Code
Detects price drift and oversell risk. Thresholds are not hard-coded — they're sampled from a bandit (10a) and grounded in the tenant's own history (10b).
Input (from node 9)
[{ "sku":"RICE-5KG","channels":{"shopify":{"qty":42,"price":480},"amazon":{"qty":38,"price":520},"pos":{"qty":45,"price":480}} }, ...]
Paste-ready Python
import numpy as np

def sampled_threshold(tenant_id, rule_id, base):
    # Pulls Beta(alpha, beta) from node 10a's memory store
    a, b = get_posterior(tenant_id, rule_id)       # default (1, 1) = uniform prior
    weight = np.random.beta(a + 1, b + 1)           # sample one value, range [0,1]
    return base * (0.6 + 0.8 * weight)              # scale into [0.6x, 1.4x] of base

# Pull tenant-calibrated base values (computed nightly by node 10b)
base_price  = get_tenant_threshold(tenant_id, "price_delta")     # e.g. 18 (was hard-coded 20)
base_oversell = get_tenant_threshold(tenant_id, "oversell_buf")  # e.g. 8

PRICE_DELTA_THRESHOLD   = sampled_threshold(tenant_id, "price_delta", base_price)
OVERSELL_BUFFER         = sampled_threshold(tenant_id, "oversell_buf", base_oversell)

conflicts = []
for sku_row in input:
    sku = sku_row["sku"]
    prices = [ch["price"] for ch in sku_row["channels"].values() if ch]
    qty_pos = sku_row["channels"]["pos"]["qty"]

    # Rule 1 — price drift across channels
    if prices and (max(prices) - min(prices)) > PRICE_DELTA_THRESHOLD:
        conflicts.append({
            "sku": sku, "type": "PRICE_DRIFT",
            "delta": max(prices) - min(prices),
            "channels": sku_row["channels"]
        })

    # Rule 2 — online listing exceeds POS stock minus safety buffer
    for online_ch in ("shopify", "amazon"):
        if sku_row["channels"][online_ch]["qty"] > (qty_pos - OVERSELL_BUFFER):
            conflicts.append({
                "sku": sku, "type": "OVERSELL_RISK",
                "channel": online_ch,
                "online_qty": sku_row["channels"][online_ch]["qty"],
                "pos_qty": qty_pos
            })

return {"conflicts": conflicts}
Line-by-line
  • sampled_threshold(...) — wrapper that performs Thompson sampling on the bandit posterior. For a rule that's been frequently accepted, the Beta distribution skews right → weight near 1 → threshold multiplied by ~1.4 (lenient). For an over-firing rule, weight is near 0 → threshold multiplied by ~0.6 (strict).
  • np.random.beta(a+1, b+1) — the "+1" is the Jeffreys prior, keeping the distribution well-defined when no data has been collected yet.
  • get_tenant_threshold(...) — pulls the empirically-calibrated P85 value written by node 10b last night. This replaces the McKinsey citation entirely.
  • max(prices) - min(prices) — cross-channel price spread. If Shopify says Rs.480 and Amazon says Rs.520, the delta is Rs.40.
  • qty_pos - OVERSELL_BUFFER — the "safe" ceiling for online listings. If POS has 45 units and the buffer is 10, we allow online listings up to 35.
Output
{ "conflicts":[{"sku":"RICE-5KG","type":"PRICE_DRIFT","delta":40,...}, ...] }
10a · Bandit Posterior Storev3Memory / Context
Per-tenant, per-rule Beta(α,β) posterior. α = accepted, β = rejected. Thompson sampling reads this; node 17a writes it.
Schema + read SQL
CREATE TABLE IF NOT EXISTS rule_posteriors (
  tenant_id   UUID    NOT NULL,
  rule_id     TEXT    NOT NULL,
  alpha       INTEGER NOT NULL DEFAULT 0,   -- times the fix was accepted
  beta        INTEGER NOT NULL DEFAULT 0,   -- times rejected
  updated_at  TIMESTAMP NOT NULL DEFAULT NOW(),
  PRIMARY KEY (tenant_id, rule_id)
);

-- READ (called from node 10):
SELECT alpha, beta
FROM rule_posteriors
WHERE tenant_id = :tenant_id AND rule_id = :rule_id;
Why this design
  • Composite PRIMARY KEY — guarantees one row per (tenant, rule) pair. Upserts are safe.
  • INTEGER counters — Beta(α,β) with integer evidence is the standard conjugate-prior formulation. No floats needed, no rounding drift.
  • Default 0 — node 10's +1 adds the Jeffreys prior at sample time.
10b · Tenant Threshold Calibratorv3Custom Code (Nightly)
Computes the P85 of this tenant's own legitimate price moves over 30 days, writes it as the base threshold. Replaces "per McKinsey 2023" with "per your own data."
Nightly cron (Superset schedule: 0 2 * * *)
-- Compute P85 of tenant's real price movements from the last 30 days
WITH legit_moves AS (
  SELECT
    sku,
    ABS(price - LAG(price) OVER (PARTITION BY sku ORDER BY ts)) AS delta
  FROM price_history
  WHERE tenant_id = :tenant_id
    AND ts > NOW() - INTERVAL '30 days'
)
INSERT INTO tenant_thresholds (tenant_id, rule, value, computed_at)
SELECT
  :tenant_id,
  'price_delta',
  percentile_cont(0.85) WITHIN GROUP (ORDER BY delta),
  NOW()
FROM legit_moves
WHERE delta IS NOT NULL
ON CONFLICT (tenant_id, rule) DO UPDATE
  SET value = EXCLUDED.value, computed_at = EXCLUDED.computed_at;
Line-by-line
  • LAG(price) OVER (PARTITION BY sku ORDER BY ts) — window function that gets the previous price for the same SKU. The ABS delta is one "move."
  • percentile_cont(0.85) — the 85th percentile. If a tenant's usual moves are Rs.2-18, P85 might be Rs.15. That's "normal." Anything above that is worth flagging.
  • ON CONFLICT ... DO UPDATE — upsert. Keeps one row per (tenant, rule), always fresh.
  • Nightly schedule — daily is enough. Price distributions don't shift hour-to-hour.

13a · Reserve Action Slot (Idempotency)v3Custom Code
Makes retries safe at the database level. A UNIQUE constraint on action_log.key means Postgres — not the app — guarantees exactly-once delivery.
Paste-ready Python
import hashlib
from datetime import date

# 1. Build a deterministic key from the intent (not the timestamp)
raw = f"{tenant_id}|{conflict['sku']}|{conflict['type']}|" \
      f"{conflict.get('channel','')}|{conflict.get('delta','')}|{date.today()}"
action_key = hashlib.md5(raw.encode()).hexdigest()

# 2. Attempt to reserve the slot. UNIQUE constraint does the work.
try:
    db.execute("""
        INSERT INTO action_log (key, tenant_id, sku, action, status, created_at)
        VALUES (:k, :t, :s, :a, 'reserved', NOW())
    """, k=action_key, t=tenant_id, s=conflict["sku"], a=json.dumps(conflict))
    return {"proceed": True, "action_key": action_key}
except UniqueViolation:
    # We've already done this exact action today — skip silently
    return {"proceed": False, "reason": "already_applied_today", "action_key": action_key}
Line-by-line
  • raw = f"..." — the intent, not the execution. Two retries of the same fix produce the same key → duplicate INSERT fails safely.
  • date.today() in the key — allows the fix to repeat tomorrow if genuinely needed. Without the date, one correct fix would be blocked forever.
  • UniqueViolation — Postgres raises this when the INSERT violates the UNIQUE constraint. We catch it and skip. The database is our source of truth, not the application.
  • No race condition — even two parallel workers trying to insert the same key simultaneously: Postgres serializes the constraint check. One wins, one gets UniqueViolation. Bulletproof.
13b · Token Bucket Circuit Breakerv3Evaluator / Guardrail
Every tenant has a 50-token Redis bucket that refills at 10/min. Every auto-fix spends 1 token. Empty = auto-mode OFF until refill. This is AWS's leaky-bucket pattern for rate-limiting.
Paste-ready Python
import time, redis, os

r = redis.from_url(os.environ["REDIS_URL"])
key = f"bucket:{tenant_id}"
now = time.time()

# 1. Read current bucket state (pipelined for atomicity)
last, tokens = r.hmget(key, "last", "tokens")
tokens = float(tokens) if tokens else 50.0
last   = float(last)   if last   else now

# 2. Refill: 10 tokens per 60 seconds, capped at 50
refill_rate = 10.0 / 60.0
tokens = min(50.0, tokens + (now - last) * refill_rate)

# 3. Check availability
if tokens < 1.0:
    emit_alert(tenant_id, "auto_mode_tripped")
    return {"proceed": False, "route": "human_handoff", "tokens_left": tokens}

# 4. Spend one token and persist
r.hmset(key, {"last": now, "tokens": tokens - 1.0})
return {"proceed": True, "tokens_left": tokens - 1.0}
Line-by-line
  • r.hmget(...) — HMGET is Redis's hash-get-multiple. One round-trip gets both "last refill time" and "current tokens."
  • (now - last) * refill_rate — the leaky-bucket math. If 30 seconds have passed and refill is 10/min, we add 5 tokens.
  • min(50.0, ...) — the ceiling. Buckets don't overflow. This prevents long-idle tenants from getting unlimited burst capacity.
  • tokens < 1.0 — can't spend what we don't have. Flip to human handoff. The bucket will refill in the background and auto-mode resumes naturally.
Output (when tripped)
{ "proceed": false, "route": "human_handoff", "tokens_left": 0.3 }

  • X-Idempotency-Key — Shopify and Amazon both honor this header. The server deduplicates, so even if the client network layer retries, the fix applies exactly once.
  • exponential + jitter — 200ms → 400ms + jitter → 800ms + jitter. The jitter breaks the thundering-herd problem where many workers retry in lockstep.
  • max 3 — beyond that, route to human handoff. A misbehaving API shouldn't burn tokens forever.

21b · Isotonic Confidence Calibratorv3Custom Code (Nightly)
Fits isotonic regression to find the raw confidence at which precision ≥ 0.9. That becomes the tenant's threshold.
Paste-ready Python (sklearn)
from sklearn.isotonic import IsotonicRegression

samples = db.query("""
    SELECT confidence, accepted
    FROM bullet_feedback
    WHERE tenant_id = :t AND accepted IS NOT NULL
    ORDER BY ts DESC LIMIT 500
""", t=tenant_id)

# Cold-start: not enough feedback yet → keep default 0.7
if len(samples) < 200:
    return {"threshold": 0.7, "mode": "cold_start"}

X = [s.confidence for s in samples]
y = [1 if s.accepted else 0 for s in samples]

# Isotonic regression learns a monotonic mapping:
# raw confidence → empirical precision (accept rate)
ir = IsotonicRegression(out_of_bounds="clip").fit(X, y)

# Find the lowest raw confidence at which precision >= 0.9
for c in sorted(set(X)):
    if ir.predict([c])[0] >= 0.9:
        write_threshold(tenant_id, "confidence", c)
        return {"threshold": c, "mode": "calibrated"}

# No confidence band hits precision 0.9 → be conservative
return {"threshold": 0.95, "mode": "conservative"}
Line-by-line
  • IsotonicRegression(...) — learns a non-decreasing function. Higher raw confidence → higher empirical accept rate, always.
  • out_of_bounds="clip" — for confidences outside the training range, extend the function flat. Safe behavior.
  • if ir.predict([c])[0] >= 0.9 — we want the lowest confidence at which the model is empirically right 90% of the time. That's the "just good enough" line.
  • Three return modes — cold_start / calibrated / conservative. Each gives the dashboard a transparency flag; the UI shows which mode is active.

23 · Regex Fact-Verifyv2Evaluator / Guardrail
Stage 1 of dual verification. Extracts every Rs. figure and SKU name from the bullet and checks set membership against the source data.
Paste-ready Python
import re

# Broadened regex: Rs, ₹, INR; with/without decimals; K-suffix
MONEY_RE = re.compile(r"(?:Rs\.?|₹|INR)\s?([\d,]+(?:\.\d+)?)\s?[Kk]?", re.I)
SKU_RE   = re.compile(r"\b[A-Z]{2,}[-_][A-Z0-9]+\b", re.I)

def normalize_money(match):
    val = match.group(1).replace(",", "")
    num = float(val)
    if match.group(0).lower().endswith("k"):
        num *= 1000
    return num

bullet = llm_output["bullet"]

# 1. Build the set of allowed Rs. values from the source conflicts
allowed_money = set()
for c in conflicts:
    allowed_money.add(float(c["delta"]))
    allowed_money.add(float(c["delta"] * c.get("daily_qty", 1)))

# 2. Build the set of allowed SKUs
allowed_skus = {c["sku"].upper() for c in conflicts}

# 3. Check every monetary claim in the bullet
for m in MONEY_RE.finditer(bullet):
    val = normalize_money(m)
    # Allow 5% tolerance — SMEs round off
    if not any(abs(val - a) / max(a, 1) < 0.05 for a in allowed_money):
        return {"ok": False, "reason": f"fake_money Rs.{val}"}

# 4. Check every SKU mention
for s in SKU_RE.findall(bullet):
    if s.upper() not in allowed_skus:
        return {"ok": False, "reason": f"fake_sku {s}"}

return {"ok": True}
Line-by-line
  • MONEY_RE — non-capturing (?:Rs\.?|₹|INR) matches any of three prefixes. [\d,]+(?:\.\d+)? handles "2,800" and "2800.50". Trailing [Kk]? catches "2.8K".
  • normalize_money — converts K-suffix to actual numbers. "2.8K" → 2800. Drops commas for arithmetic.
  • 5% tolerance — accepts "Rs.2,800" when the source says Rs.2,804. SMEs round naturally. Zero tolerance would cause false rejections.
  • allowed_skus / allowed_money as SETS — O(1) lookups.
  • Early return on failure — if any number or SKU is unsourced, we refuse the bullet. The dashboard shows the last-good bullet instead.

27b · Self-Consistency Intersectv3Custom Code
Publishes only claims that appear in BOTH runs. One-off hallucinations are filtered out.
Paste-ready Python
import re

MONEY_RE = re.compile(r"(?:Rs\.?|₹|INR)\s?([\d,]+(?:\.\d+)?)\s?[Kk]?", re.I)
SKU_RE   = re.compile(r"\b[A-Z]{2,}[-_][A-Z0-9]+\b", re.I)

def claim_set(bullets):
    """Canonicalize each bullet into (money_set, sku_set) tuples."""
    claims = set()
    for b in bullets:
        money = frozenset(m.group(1).replace(",","") for m in MONEY_RE.finditer(b))
        skus  = frozenset(s.upper() for s in SKU_RE.findall(b))
        claims.add((money, skus))
    return claims

claims_a = claim_set(run_a["bullets"])
claims_b = claim_set(run_b["bullets"])

# Intersection — only keep bullets whose (money, sku) signature appears in BOTH runs
agreed  = claims_a & claims_b
if len(agreed) == 0:
    # Hard disagreement — fall back to most conservative single bullet
    return {"bullets": [run_a["bullets"][0]], "warning": "self_consistency_failed"}

# Keep Run A's phrasing for the claims that survived
kept = [b for b in run_a["bullets"]
        if (frozenset(m.group(1).replace(",","") for m in MONEY_RE.finditer(b)),
            frozenset(s.upper() for s in SKU_RE.findall(b))) in agreed]

return {"bullets": kept, "runs_agreed": len(agreed)}
Line-by-line
  • claim_set — canonicalizes each bullet into a "fingerprint" of its factual claims (money + SKUs). Two differently-worded bullets that make the same claim produce the same fingerprint.
  • frozenset — needed because sets are unhashable; frozensets are hashable and can go inside the outer set.
  • claims_a & claims_b — Python set intersection. Only fingerprints present in both runs survive.
  • Hard disagreement fallback — if both runs produce totally different claims, publish only the safest single bullet and flag the memo for human review.

33 · Drift Detector (KS + CUSUM)v3Custom Code
Runs Kolmogorov-Smirnov 2-sample test on confidence distributions, plus CUSUM on rejection rate. Any trigger fires → drift = true.
Paste-ready Python (scipy)
from scipy.stats import ks_2samp

def detect_drift(recent, baseline, trip_count, rejection_rate_pct):
    alerts = []

    # 1. Distribution drift on confidence (KS test)
    if len(recent) >= 30 and len(baseline) >= 30:
        stat, p = ks_2samp(recent, baseline)
        if p < 0.05:
            alerts.append({
                "signal": "confidence_distribution_shift",
                "p_value": p, "ks_stat": stat
            })

    # 2. Spike in circuit breaker trips
    if trip_count >= 3:
        alerts.append({"signal":"auto_mode_trips","count":trip_count})

    # 3. Rejection rate above 35% (safe SLO bound)
    if rejection_rate_pct and rejection_rate_pct > 35:
        alerts.append({"signal":"high_rejection_rate","pct":rejection_rate_pct})

    return {"drift": len(alerts) > 0, "alerts": alerts}
Line-by-line
  • ks_2samp — compares two distributions, returns the KS statistic and a p-value. p < 0.05 means "these distributions are statistically different."
  • Three independent signals — distribution shift, spike in trips, elevated rejections. Any one firing is enough; we'd rather over-alert than miss drift.
  • Minimum sample size 30 — below that, KS is unreliable. We skip the test rather than produce false alarms.
  • Returns the alerts list — node 34's prompt gets the raw alert data and explains it in natural language.
